🛠️ Le Script d'Actualisation des Quotas

Le script scripts/providers/refresh.py automatise la détection, la mesure des quotas réels et l'ajustement du fichier de configuration llm_module/config/providers.yaml.

make providers
Sonde les providers réels et applique les modifications au YAML
make providers DRY_RUN=1
Prévisualise le bilan et les alarmes sans toucher au fichier
📡 Sources de données par Adapter
  • Mistral / Groq / Cerebras : 1 requête sonde minimale (max_tokens=1) → extraction des en-têtes HTTP x-ratelimit-*.
  • Google : Requête directe sur l'API Cloud Quotas (cloudquotas.googleapis.com) avec le token gcloud auth print-access-token sur le projet actif.
  • OpenAI : Pas de sonde automatique sans clé configurée dans .env.
🔄 Cycle de vie des modèles
  • Nouveau modèle détecté : Découvert via GET /models. Si RPD ≥ 100 → inclus en rotation avec calcul de poids. Si RPD < 100 → weight: 0 (hors rotation).
  • Modèle disparu : Automatiquement commenté avec la date du jour et marqué par une [ALARME] dans le rapport.
  • Édition chirurgicale : Seuls les scalaires modifiés sont réécrits, les commentaires humains et blocs archivés sont strictement préservés.

⚖️ Règles d'Application & Rate Limiting

1. Quotas par Minute (RPM & TPM)

Gérés par réservation atomique Lua dans Redis sur des fenêtres glissantes de 60 secondes. Le micro-batching ajuste la taille maximale des lots (batch_max_agents) :
batch_max = max(1, min(tpm / 3000, req_cap / 3000, rpm, 20))

2. Quotas Journaliers (RPD & TPD)

Compteurs journaliers réinitialisés à 00:00 UTC. Dès qu'un provider atteint son rpd_limit ou tpd_limit, le répartiteur de charge l'écarte automatiquement de la rotation jusqu'au lendemain au lieu d'attendre un simple timeout.

💡 Diagnostic et suivi post-simulation

Pour analyser a posteriori l'utilisation des quotas d'un run et vérifier qu'aucune minute n'a subi de saturation 429 ou de dépassement de débit, utilisez :
python3 scripts/debug/quota_validator.py experiments/current ou make capacity.

🎯 Rôles Clés en Calibration : Juge vs Mutateur

Dans le module de calibration génétique des prompts (prompt_calibration), les modèles Google Gemini sont strictement partitionnés pour maximiser les quotas et stabiliser les scores :

👨‍⚖️ Le Juge d'Évaluation : google_gemini31

Modèle : gemini-3.1-flash-lite-preview (alias stable gemini-3.1-flash-lite)
Quota : 500 requêtes/jour dédiées.
Règle : Aucune réflexion (thinking = 0). Épinglé dans la clé de cache RunConfig.eval_params_key(). Ne jamais modifier sous peine d'invalider tout le cache d'évaluations.

🧬 Le Générateur / Mutateur : google_gemini35

Modèle : gemini-3.5-flash-lite
Quota : 500 requêtes/jour indépendantes du juge.
Règle : Dispose d'un budget de pensée (mutation_thinking_budget: 1024 tokens) pour concevoir et croiser de meilleurs prompts sans influencer la note du juge.
